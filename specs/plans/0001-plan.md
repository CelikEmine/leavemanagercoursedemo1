   Java 17 and Node.js 22 are available locally before BUILD. Use Maven Wrapper, Spring Boot
   4.1.2, Node.js 22 LTS, React 18, PostgreSQL 17, JUnit 5/Mockito, Vitest/Testing Library and Playwright.
   PostgreSQL integration tests
   run in CI against its PostgreSQL service container; local `full` is intentionally unavailable.
2. **Create the smallest backend slice.** Add a Spring application and readiness behavior that
   reports ready only when PostgreSQL is reachable; configure isolated test data.
3. **Create the frontend slice.** Add the accessible loading, ready and unavailable screen
   states. The screen must not infer readiness from a successful page load alone.
4. **Add tests.** Cover backend readiness, PostgreSQL connectivity, component states, and the
   one browser smoke journey. Keep test selectors complementary so every test runs in exactly
   one profile.
5. **Activate verification.** Replace planned comments in `scripts/check.conf` with real
   commands and prerequisites. Fast includes compile/lint/unit/component; full adds
   integration/E2E and requires CI's PostgreSQL service. Commands must use run-once/no-daemon
   behavior and clean up their processes, browser and test data in the same step, preserving exit
   codes. No local container runtime prerequisite is added.
6. **Wire CI and documentation.** Configure CI Java/Node toolchain and a PostgreSQL service
   container, run the full contract there, and document local fast/CI full commands, tools,
   selectors, E2E budget and cleanup behavior.
7. **Verify.** Run doctor and fast checks locally; run full check and both residue profiles in CI.
   Confirm test counts and profile durations (median of at least three runs), record exact
   evidence, and ensure the CI full green matches the candidate commit.

## Risks & open questions
- **R-1 — Per-profile execution environment (R-13 decision recorded).** At planning, this machine
  had JDK 17 and Node.js 22.23.4, but no WSL2, Docker or Podman. The user later enabled WSL and
  restarted the machine; this does not change the approved CI-only `full` profile, whose
  prerequisites intentionally require CI and its PostgreSQL service.
  **Human decision:** local `fast`; `full` (PostgreSQL integration and E2E) in CI with a
  PostgreSQL service container. **Recommendation:** configure prerequisites so doctor reports
  local `full` as unavailable and CI `full` as runnable; do not make BUILD wait for local WSL or
  a container runtime.
- **R-2 — Framework support and dependency selection (resolved by user decision).** The bootstrap
  selected Spring Boot 2.7, but Spring's official policy says minor releases are supported for at
  least 12 months and 2.7 is outside that window. The user approved upgrading to Spring Boot 4.1.2.
  The [official Spring Boot system requirements](https://docs.spring.io/spring-boot/system-requirements.html)
  state Java 17 is the minimum; [Spring's support policy](https://github.com/spring-projects/spring-boot/wiki/Supported-Versions)
  says minor releases are supported for at least 12 months. Maven Central lists 4.1.2 as a
  released artifact while 4.2.0 is a release candidate
  ([version metadata](https://repo.maven.apache.org/maven2/org/springframework/boot/spring-boot-starter-parent/maven-metadata.xml)).
  **Recommendation:** pin 4.1.2 and use its managed dependencies; reconsider only if a verified
  compatibility issue arises.
- **R-3 — CI service-dependent tests.** PostgreSQL integration tests and the browser journey need
  deterministic startup and cleanup. **Recommendation:** use an isolated PostgreSQL service per
  CI job; one test-runner component owns the app/browser lifecycle and stops them even on failure
  or timeout.
- **R-4 — E2E scope.** The proposed budget is one readiness smoke journey, at most two minutes;
  Playwright is a recommendation, not yet approved. **Recommendation:** keep this as the only
  browser journey and prove other states in component tests.
- **R-5 — Module boundaries.** `specs/backlog.md` B-1 records that boundaries were deferred.
  **Recommendation:** decide only the minimum testable boundary needed for the readiness slice;
  defer broader module decomposition rather than expanding this feature.
